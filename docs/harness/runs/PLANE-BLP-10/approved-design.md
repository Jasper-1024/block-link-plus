<p># Design Intake: BLP-10</p>
<p>## Status</p>

<p>## Plane Reply</p>
<p>Human approval was confirmed on 2026-08-25 for the bounded File Outliner Alt+ArrowUp/Down design. Use standard Obsidian commands with default hotkeys that users can rebind, a persistent movement-mode setting defaulting to Same-level only, atomic source and target subtrees, and a non-crossable Zoom root. The item is ready for <code>Review Approved</code> and implementation routing.</p>
<p>## Current Understanding</p>
<p>BLP-10 is a Plane-only enhancement with the <code>cdp-required</code> label. It asks for VS Code-style Alt+ArrowUp/Down movement of the block containing the current cursor, including its nested child subtree, with clean boundary no-ops and best-effort preservation of editor focus, cursor/selection, content, and view position.</p>
<p>The user-visible mode choices are:</p>
<ul><li><strong>Same-level only:</strong> move only among sibling blocks at the same nesting level;<br>do not change indentation or cross a parent/child boundary.</li><li><strong>Cross-level align:</strong> use the previous/next block regardless of nesting and<br>align the moved block&#x27;s indentation to that adjacent target.</li></ul>
<p>Human review fixed the remaining product choices: the feature is only a faster alternative to existing drag-and-drop in File Outliner; both source and target blocks move as complete subtrees; the Zoom root is a hard movement boundary; the movement mode is the only new BLP setting; and shortcut customization uses Obsidian&#x27;s standard Hotkeys UI.</p>
<p>The source issue contains the full claim and acceptance criteria; there is no configured external issue to fetch. The current worktree is the reset master baseline mentioned by the latest tracker feedback, so the prior implementation and saved traces are not treated as current product evidence. The current runtime baseline below was collected again from the task-owned instance.</p>

<h4>Existing block model and structural seams</h4>
<ul><li><code>src/features/file-outliner-view/protocol.ts:30</code> models each<br><code>OutlinerBlock</code> as a node with <code>depth</code>, editable <code>text</code>, and nested<br><code>children</code>. This makes the block plus descendants the existing natural<br>atomic move unit.</li><li><code>src/features/file-outliner-view/engine.ts:338</code> and <code>:400</code> already provide<br>linearize/rebuild-based indentation operations that preserve visible order.<br><code>moveBlockSubtree</code> at <code>:443</code> already moves a tree node before/after another<br>node for drag/drop, rejects moves relative to descendants, and recomputes<br>depths. It currently returns a zeroed selection and has no movement-mode or<br>cross-level target selection semantics, so it should be extended or wrapped<br>rather than called directly for the keyboard feature.</li><li><code>src/features/file-outliner-view/view.ts:1925</code> is the shared structural<br>application boundary. It records view-local undo/redo snapshots, marks dirty<br>blocks, schedules persistence, rebuilds the DOM, restores focus, and captures<br>the viewport when <code>scroll</code> is false. Routing keyboard movement through this<br>boundary avoids creating a second history or focus model.</li><li>The current selection type is <code>{ id, start, end }</code>. <p>## Discussion Questions</p>
<p>All design questions were resolved by human review on 2026-08-25.</p>
<ol><li><strong>Which editor surfaces own the shortcut? �X Confirmed</strong></li></ol>
<p>Decision: scope the first implementation to focused <code>FileOutlinerView</code> editors, including a detached/embedded Outliner instance when its own editor has focus; do not add structural movement to the native Markdown editor or Inline Edit Embed.</p>
<p>Why it matters: the existing <code>OutlinerBlock</code> tree and structural history only exist in <code>FileOutlinerView</code>. Extending native Markdown would require a separate parser, selection model, and persistence contract rather than a bounded BLP change.</p>
<ol><li><strong>How are Alt+ArrowUp/Down registered? �X Confirmed</strong></li></ol>
<p>Decision: add two standard Obsidian commands with default Alt+Arrow hotkeys and <code>checkCallback</code> availability limited to an active File Outliner block editor. Users may remove or rebind them in Obsidian Hotkeys. Do not register duplicate fixed CM6 Alt+Arrow bindings. Both commands call one view interface, <code>moveActiveBlock(up | down)</code>, so one keypress has one execution path.</p>
<p>Why it matters: standard commands provide discoverability and rebinding, while a single execution path prevents a block from moving twice.</p>
<ol><li><strong>What is the default movement mode? �X Confirmed</strong></li></ol>
<p>Decision: default to <code>same-level</code> (Same-level only).</p>
<p>Why it matters: this is the least surprising and least destructive behavior for existing Outliner users; it never changes indentation. Users can opt in to cross-level indentation rewrites through the persisted setting.</p>
<ol><li><strong>What is the target and Zoom behavior? �X Confirmed</strong></li></ol>
<p>Decision: use the immediate previous/next eligible block in the current visible Outliner scope, excluding the current subtree and collapsed hidden descendants. Treat both the current block and the target block as complete subtree units. Move before the target subtree for Up or after the target subtree for Down, align the moved root to the target root&#x27;s depth, and preserve descendant-relative depths. The current Zoom root is not eligible as a crossable target; movement at that boundary is a handled no-op.</p>
<p>Why it matters: this matches the visible Outliner operation, prevents cycles and stale out-of-scope DOM, and avoids moving the active editor out of a Zoom context.</p>
<ol><li><strong>Which behavior is configurable? �X Confirmed</strong></li></ol>
<p>Decision: add one global persisted dropdown under Outliner �� Editing with the two explicit mode labels. Read it at invocation time so changes apply to the next move without reload. Do not add a per-file override, transient menu, toolbar action, or automatic mode switch.</p>
<p>Why it matters: movement policy is a genuine user preference; subtree, Zoom, history, focus, and persistence rules remain stable correctness invariants rather than a growing matrix of settings.</p>
<p>## Candidate Scope</p>
<p>After human approval, the smallest coherent implementation slice is:</p>
<ol><li>Add a persisted <code>FileOutliner</code> movement-mode union and conservative default,<br>merge it through <code>DEFAULT_SETTINGS</code>, and render the two options in the<br>existing Outliner Editing settings group with English, Simplified Chinese,<br>and Traditional Chinese labels.</li><li>Add a pure engine operation for direction + mode that:</li></ol>
<ul><li>treats the selected block and all descendants as one source subtree;</li><li>selects only the adjacent direct sibling subtree in Same-level mode;</li><li>selects the immediate eligible visible-scope neighbor outside the source<br>subtree in Cross-level align mode, treating the target and its descendants<br>as one atomic subtree rather than exposing collapsed descendants as<br>individual targets;</li><li>treats the current Zoom root as a non-crossable boundary;</li><li>moves the source before the target subtree for Up or after the target<br>subtree for Down, keeps block text and ids unchanged, aligns the source<br>root to the target root in Cross-level mode, preserves descendant-relative<br>depths, and recomputes valid absolute depths;</li><li>returns the original block selection for a successful move and a<br><code>didChange: false</code> result at boundaries or invalid targets; and</li><li>reports every affected block id needed for correct rendering/persistence,<br>including descendants whose indentation changes.</li></ul>
<ol><li>Add one view interface, <code>moveActiveBlock(up | down)</code>, and register two<br>standard Obsidian commands whose default Alt+Arrow hotkeys users can remove<br>or rebind through Obsidian Hotkeys. Do not add duplicate fixed CM6 Alt+Arrow<br>bindings. Route successful moves through <code>applyStructuralEngineResult</code> so<br>undo/redo, stale-editor protection, focus, cursor range, viewport<br>restoration, and debounced save behavior remain centralized. A handled<br>boundary no-op must create no history entry, dirty state, or save.</li><li>Add focused unit tests for command availability and single dispatch,<br>same-level sibling-subtree movement, source/target subtree preservation,<br>cross-level up/down alignment, collapsed descendants and Zoom boundaries,<br>selection preservation, invalid-target no-ops, setting defaults and<br>persistence, and structural-history integration.</li><li>Rebuild/reload the plugin and collect CDP proof in the implementation stage<br>using a mixed-depth temporary note. The proof should cover the default and<br>rebound commands, exactly one move per invocation, both movement modes,<br>top/bottom and Zoom-root no-ops, atomic source/target subtree movement,<br>immediate setting changes and persistence after reload, on-disk<br>indentation/order, one-step undo/redo, focus/cursor/selection, and viewport<br>stability. The implementation artifact must record exact commands and<br>post-change trace output.</li></ol>
<p>## ADR Candidates</p>
<p>None. The recommended design extends the existing pure engine and view-local structural-history seams and adds a reversible persisted setting. It does not introduce a hard-to-reverse boundary or a surprising architecture decision. Reconsider an ADR only if approval expands the feature to native Markdown editing, a shared cross-view reorder service, or a new global history model.</p>
<p>## Non-Goals</p>
<ul><li>Structural movement in the native Markdown editor, arbitrary Markdown<br>blocks, or Inline Edit Embeds.</li><li>Moving a block-range selection or multiple independently selected blocks;<br>the first slice acts only on the block owning the active editor selection.</li><li>Changing drag/drop semantics, zoom/collapse behavior, block IDs, protocol<br>versioning, cross-file moves, or the existing Outliner serialization format.</li><li>Crossing the current Zoom root or acting through a stale editor outside the<br>active visible Outliner scope.</li><li>Adding duplicate fixed CM6 Alt+Arrow bindings alongside the standard Obsidian<br>commands.</li><li>Adding a per-file mode override, automatic mode switching, quick menu,<br>toolbar control, or a second transient menu state.</li><li>Replacing CodeMirror text history or creating a new global undo journal;<br>keyboard moves remain one view-local structural history entry each.</li><li>Claiming post-change command behavior, indentation alignment, persistence,<br>or focus/scroll validation during design intake; those remain implementation<br>and CDP validation gates.</li></ul>
