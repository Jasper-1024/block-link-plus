<p>## Plane Reply</p>
<p>Human decision needed: approve or reject a bounded extension of current-note document search (<code>editor:open-search</code>) in normal Markdown Live Preview. The recommendation is to aggregate the host editor with BLP-owned inline-edit embed editors, search only their visible ranges, and leave Global Search, Reading View, and native preview embeds unchanged. The runtime proves the gap and also exposes a hidden-range compatibility risk; details are in the runtime trace below.</p>
<p>Move the item to <code>Review Approved</code> to authorize implementation routing, or to <code>Review Rejected</code> with feedback. Keep it in <code>Human Review</code> if the command, range, or compatibility decisions remain unresolved.</p>
<p>## Current Understanding</p>
<p>GitHub issue #39 asks for Obsidian to find text inside embedded blocks, headings, and notes while a note is in Live Preview; the report says the same behavior is available in Reading View. The Plane description deliberately leaves search ownership, scope, and compatibility open. There are no GitHub comments or prior human-review comments to reconcile.</p>
<p>The request most closely matches current-note document search rather than the vault-wide Search pane: Live Preview currently has a host CodeMirror document plus BLP-owned detached CodeMirror editors for inline embeds, while Global Search indexes source files independently. This interpretation needs the human decision in Question 1.</p>
<p>In the current plugin, the affected embed forms map to existing settings:</p>
<ul><li><code>inlineEditBlock</code>: <code>![[file#^blockId]]</code> and range/block embeds</li><li><code>inlineEditHeading</code>: <code>![[file#Heading]]</code></li><li><code>inlineEditFile</code>: <code>![[file]]</code> (disabled by default)</li></ul>
<p>Reading View remains read-only in the existing product contract. No product code, tests, package metadata, generated files, or formal specs were changed for this intake.</p>
<p>## Repo Findings</p>
<p><code>InlineEditEngine</code> is the natural ownership seam for the requested behavior:</p>
<ul><li><code>InlineEditEngine.ts:957-1118</code> observes normal Markdown Live Preview DOM and<br>mounts eligible embeds as they appear.</li><li><code>InlineEditEngine.ts:1311-1337</code> parses block, heading, and full-file embeds<br>according to the existing settings.</li><li><code>EmbedLeafManager.ts:81-130</code> creates a detached <code>WorkspaceLeaf</code> with a<br><code>MarkdownView</code>; the embed surface is therefore a separate CodeMirror editor,<br>not part of the host editor&#x27;s document.</li><li><code>InlineEditEngine.ts:293-315</code> tracks focus for those managed embeds.<br><code>InlineEditEngine.ts:711-879</code> routes editor commands to the focused detached<br>editor and temporarily exposes that editor as the active view/leaf while a<br>command runs. This explains why search works when an embed already owns<br>focus, but does not aggregate searches from a host-focused note.</li><li><code>selectiveEditor.ts:111-119</code>, together with the range annotations applied at<br><code>InlineEditEngine.ts:1795-1812</code>, hides source lines outside an embed&#x27;s<br>rendered range and hides Outliner system-tail lines. Native CodeMirror<br>search still searches the full underlying document, so search scope cannot<br>be assumed from the visual decorations.</li><li>Existing tests cover inline-edit mounting/lifecycle, shell preservation,<br>range hiding, and file-embed parsing, but there is no search-specific<br>coordinator or regression test.</li></ul>

<p>## Discussion Questions</p>
<ol><li>**Which Obsidian search surface does #39 change: current-note document<br>search or Global Search?**</li></ol>
<p>Recommended answer: extend current-note <code>editor:open-search</code> in normal Markdown Live Preview only; leave <code>global-search:open</code> and its source-file index unchanged.</p>
<p>Why it matters: the two commands have different result models. Aggregating Global Search would change vault-wide indexing and duplicate source-file results, while the reproduced defect is that a host-focused Live Preview editor cannot see text rendered by its embedded editors.</p>
<ol><li>**Should the feature search only BLP-owned inline-edit surfaces, or also<br>native preview embeds that BLP leaves untouched?**</li></ol>
<p>Recommended answer: search only mounted BLP-owned embed editors and honor <code>inlineEditBlock</code>, <code>inlineEditHeading</code>, and <code>inlineEditFile</code>; a full-note embed participates only when <code>inlineEditFile=true</code>.</p>
<p>Why it matters: BLP has reliable ownership, focus, and lifecycle handles for detached CodeMirror editors. Scanning or indexing native preview DOM would create a second renderer/search contract and would make the default <code>inlineEditFile=false</code> behavior ambiguous.</p>
<ol><li>**For block and heading embeds, should matches be limited to the visible<br>rendered range or search the full underlying source document?**</li></ol>
<p>Recommended answer: search the visible range, including visible read-only heading or range-marker lines, while excluding hidden source lines and Outliner system-tail lines.</p>
<p>Why it matters: the current detached editor retains the whole source note; runtime evidence shows native search returns <code>1 / 1</code> for a heading token hidden outside a block embed&#x27;s displayed range. Full-document matching would surface text the user cannot see in that embed and could expose BLP maintenance tokens.</p>
<ol><li>**How should the native search UI count and navigate matches across the<br>host and repeated embed occurrences?**</li></ol>
<p>Recommended answer: use occurrence-based counts for the current rendered note, reuse the native document-search panel, and when the next match is in an embed, focus that editor and reveal the matching visible line. Repeated references to the same source count as separate visible occurrences.</p>
<p>Why it matters: a single source note can appear in multiple embeds or ranges. De-duplicating by source file would make navigation jump to a different occurrence than the one represented in the current note.</p>
<ol><li><strong>What Obsidian compatibility boundary is acceptable for the implementation?</strong></li></ol>
<p>Recommended answer: keep the first slice behind a narrow InlineEditEngine adapter for normal Markdown Live Preview, compose with the existing native search panel where possible, fail open to native single-editor search, and avoid changing Global Search or introducing a global command patch.</p>
<p>Why it matters: the current solution already relies on detached <code>WorkspaceLeaf</code>/<code>MarkdownView</code> internals and temporary active-view routing. A plugin-owned aggregate search UI or a broad interception of Obsidian&#x27;s private search internals would increase version and lifecycle risk. If that narrow adapter is not viable on the supported Obsidian version, the choice between a private native-panel integration and a plugin-owned UI needs a separate human decision.</p>
<p>## Candidate Scope</p>
<p>After approval, the smallest coherent implementation slice is:</p>
<ul><li>Normal Markdown <code>MarkdownView</code> in Live Preview only.</li><li>Current-note document search initiated from the host editor, aggregating the<br>host CodeMirror editor with the BLP-managed inline-edit editors mounted in<br>that host.</li><li>Block, heading, and full-note embeds only when their existing inline-edit<br>settings allow BLP to own the surface.</li><li>Visible-range matching with explicit exclusion of hidden lines and<br>Outliner system-tail lines; visible read-only heading/marker text remains<br>searchable.</li><li>Native-looking count/navigation behavior that focuses and reveals a<br>matching embed without changing source content.</li><li>No behavior change when no managed embeds are present, inline edit is<br>disabled, or native search cannot be extended safely; the host falls back to<br>its current single-editor behavior.</li></ul>
<p>Implementation routing should turn the approved choices into characterization tests for ownership/range behavior and a CDP regression covering host search, block/heading/file embed matches, navigation, repeated occurrences, settings gates, and cleanup across Live Preview lifecycle changes.</p>
<p>## ADR Candidates</p>
<p>None is required for the bounded first slice as described. If human approval requires patching Obsidian&#x27;s private search implementation globally, or introducing a plugin-owned cross-editor search protocol that becomes a long- term command-ownership boundary, record an ADR before implementation: that choice is surprising without context, hard to reverse, and has a real compatibility trade-off. A narrow InlineEditEngine-local adapter does not yet meet that ADR bar.</p>
<p>## Non-Goals</p>
<ul><li>Changing Global Search&#x27;s vault-wide index or making source-file results list<br>every embed occurrence.</li><li>Changing Reading View search behavior or making Reading View editable.</li><li>Searching native preview embeds that BLP does not own when the corresponding<br>inline-edit setting is disabled.</li><li>Covering File Outliner View, Journal Feed, <code>blp-view</code>, or other custom BLP<br>surfaces in the first slice.</li><li>Recursing into nested embeds; the current inline-edit contract intentionally<br>skips editor-in-editor mounting.</li><li>Search-and-replace across multiple editors or read-only visible ranges.</li><li>Changing embed syntax, default inline-edit settings, source-file indexing,<br>or Outliner metadata semantics.</li></ul>
